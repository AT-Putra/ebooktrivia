# R12: Midtrans sandbox recording (US-005)

Date: 2026-11-21. Environment: Midtrans **sandbox** (`app.sandbox.midtrans.com`, `api.sandbox.midtrans.com`), the Owner's sandbox merchant account.
Docs read the same day (URLs in [api-audit.md](api-audit.md)). The fixtures are in `infra/midtrans-stub/fixtures/` (scrubbed); the stub replays them and
`infra/midtrans-stub/src/replay.test.ts` pins its answers to them.

## How it was recorded

- The server key came only from the Owner's gitignored `.env.spikes`; the run refused to start unless it began with `SB-Mid-server-`. No value is in any fixture, test or document.
- Snap transactions were created with the adapter's request shape (all 14 `enabled_payments` codes, `expiry`, `callbacks.finish`) and paid on the real Snap page
  (redirect mode, `redirect_url`) in a browser with the documented test cards, and with the Midtrans payment simulators (BCA VA, QRIS). Every answer was read back with
  `GET /v2/{order_id}/status`, and the signature formula was checked on every one of them.
- Scrub: order ids, transaction ids, merchant id (and the merchant's display name), VA numbers, bill keys, payment codes, amounts and times are stable placeholders
  (`ORDER-n`, `00000000-0000-4000-8000-...`, `G000000000`, `50000.00`); signatures are recomputed over the scrubbed values with the dev key `SB-Mid-server-DEVONLY`.
- **Not recorded: a real HTTP notification delivery.** The sandbox posts to the notification URL set in the dashboard (or the per-request `X-Override-Notification` header), and this
  machine has no public URL (no tunnel, no third-party catcher was used). Midtrans documents the notification as the same fields as Get Status, so `notification.json` reuses the
  recorded status bodies. Verify one real delivery on staging (US-014/US-032).

## What else the recording showed

- **Get Status is HTTP 200 for everything found OR not found.** The state is `status_code` in the body: `200` settlement, capture, cancel; `201` pending; `202` deny; `407` expire; `404` not found.
  A Snap order whose buyer has not picked a method yet answers `{"status_code":"404","status_message":"Transaction doesn't exist.","id":"<uuid>"}` (the same as an unknown order id). The adapter reads
  both the HTTP status and the body `status_code`, so it handles this; the stub used to answer a real HTTP 404.
- **Deny, then retry on the same order (Snap's own "change payment method").** A bank-declined card gave `deny` (`status_code 202`, `bank`, `channel_response_code 05`); choosing BCA VA on the same page and the same `order_id` gave a NEW
  `transaction_id`, status `pending` (`201`), and a later simulator payment gave `settlement` (`200`). The order id is the same throughout; the denied transaction is not visible any more through Get Status.
- **Card success is `capture`, not `settlement`:** `transaction_status: "capture"`, `fraud_status: "accept"`, `status_code: "200"`, `settlement_time` already set. The docs say it becomes `settlement` the next day, and that capture is safe to treat as paid.
  `confirmSettlement` used to accept `capture` only when `treatCardCaptureAsPaid` was on (default off), and `recordPayment` stamped `settled_at` only for `settlement`, so a card buyer
  waited until the next day. **Owner decision D10 (below): capture + accept is PAID by default.**
- **Reuse of an `order_id`.** While no method was chosen, a second create with the same id answers `201` with a NEW token. Once a method was chosen: `400 {"error_messages":["transaction_details.order_id sudah digunakan"]}` (Indonesian), for a
  pending, denied-then-pending, expired or cancelled transaction; after a settlement: `400 ["transaction_details.order_id has already been taken"]` (English). **An order id expired through `POST /v2/{id}/expire` was refused too** (the docs say it can be reused).
  Our `{publicId}-{n}` scheme never reuses an id, which is why this is safe.
- **Expiry.** `expiry.unit` accepts `minute`, `minutes`, `hour`, `hours`, `day`, `days` (`seconds` is refused: "expiry must be greater than 20 seconds"). **Without `start_time` the clock starts when the buyer picks the method**
  (created about 17:31, BCA picked 17:32:29, `expiry_time` 18:32:29 for 60 minutes). With `start_time` it is pinned: `expiry_time = start_time + duration` even when the method is picked 2.5 minutes later.
  `start_time` is `yyyy-MM-dd HH:mm:ss +0700` (WIB). A start in the past is fine while `start_time + duration` is still in the future; otherwise `400 "expiry must be greater than the current time"`. All Midtrans times in answers are WIB wall clock.
- **Transaction management.** `POST /v2/{id}/expire` -> HTTP 200, body `status_code "407"`, then status `expire` (`407`). `POST /v2/{id}/cancel` -> `status_code "200"`, status `cancel` (`200`).
  Refunds could not be recorded: a refund of a `capture` card answered `412 "Transaction status cannot be updated"` (it must settle first) and of a settled VA `418 "Payment Provider doesn't allow refund within this time"`
  (both inside an HTTP 200). `refund`, `partial_refund`, `chargeback`, `partial_chargeback` are DOCS-ONLY.
- **Errors.** Wrong key: `401 {"error":"Unauthorized"}` on Snap and on Get Status. Missing `order_id`: `400 {"error_messages":["transaction_details.order_id is required"]}`.
- **Fields beyond ours:** every status carries `merchant_id`, `expiry_time`, `transaction_time` and (when settled) `settlement_time`. Card answers add `channel`, `on_us`, `bank`, `card_type`, `masked_card`; VA answers add `payment_amounts[]`.

## Changes made because of this recording

1. `createSnapTransaction` sends `expiry.start_time` (new optional `startTime`, default now); the checkout passes the instant its `snap_expires_at` counts from, so the Midtrans window and ours end together. Tests: adapter, stub, checkout int.
2. The notification route answers **503 instead of 500** for a database error or any unexpected failure, because Midtrans retries a 500 only once. Test: `webhook.int.test.ts`. The comment of the route says why.
3. `midtrans-stub` replays the recording (see `app.ts`): HTTP 200 with a `404` body, the two duplicate texts, a new token while no method is chosen, VA/Permata/Mandiri/Indomaret/QRIS/card fields, WIB times, `expiry_time`, 401 body.
   Control plane additions: `bank` and `method_chosen` in `POST /__stub/transactions/:id/state`.

## 3-D Secure (security review item, recorded 2026-11-21)

The Snap docs say `credit_card.secure` defaults to true. On the Owner's sandbox account it does **not**:

| Snap request body | Test card | What the Snap page did | Status answer |
|---|---|---|---|
| `credit_card: { secure: true }` | `4916 9940 6425 2017` (Visa, 3DS 2 challenge, accept) | a **3DS 2 challenge iframe** ("Midtrans Mock Payment Provider 3DS 2.0", password `112233`) | `capture`, fraud `accept`, `status_code 200`, **`three_ds_version: "2"`, `challenge_completion`, `eci`** |
| no `credit_card` block | the same card | **no 3DS step at all**: straight to "Payment successful" | `capture`, fraud `accept`, `status_code 200`, none of the 3DS fields |

`secure: false` was accepted by Snap (201) too (not paid in the browser: the no-block run already shows the account default is "no 3DS"). So the adapter now
sends `credit_card: { secure: true }` whenever cards can be offered (`credit_card` in the enabled list, or no list): `createSnapTransaction`, tested in the adapter, the stub fixture and the checkout
integration test. A request without `credit_card` in the list carries no `credit_card` block. Confirm the same on the first production card order. No card number beyond the public
test cards of the Midtrans docs, no key and no personal data was used or printed.

## Owner rulings on these findings (implemented, no migration)

Details for the Owner and the operator are in [docs/runbooks/payments.md](../runbooks/payments.md).

- **D9, settlement reversed to deny (Permata VA, Mandiri Bill, Indomaret; also a captured card that is cancelled).** Delivery stays instant. When a PAID order's
  attempt that held the money turns deny, cancel, expire or failure (notification or reconciliation) the order moves to `review` (D5: eligibility suspended), the
  buyer's live magic links are revoked (`public.revoke_player_magic_links`, `sql/functions.sql`, worker only), and a persisted critical `payment_paid_reversed`
  alert is raised. Nothing already sent is reversed; a later settlement restores the order. A deny of an attempt that never held money is still ignored; with
  another attempt holding money it only warns. "Held the money" is the attempt's `payments.settled_at` (stamped once), not its last status, so an intermediate pending or
  unknown status cannot hide a later reversal (fails closed); a `cancel` is gated on it too. The links are revoked only when the player has no eligible program left
  (`revoke_player_magic_links` returns 0 otherwise); nothing issues a new link, so a restored buyer logs in with an OTP, the login page's self-service resend (US-027) or an Owner re-send.
  Re-queries are ordered by the database clock (`requeryInstant`). Code: `order-machine.ts` (`eventAttemptHeldMoney`), `payment.ts`, `apps/worker/src/payments.ts`.
- **D10, cards.** `capture` with fraud accept is PAID by default (`treatCardCaptureAsPaid` now defaults to true). A capture with challenge or deny stays unpaid;
  the settlement of the next day for the same order is idempotent. `orders.paid_at` and `payments.settled_at` are stamped at the capture and set once (a later
  settlement does not touch them, so ET081 never fires). `payments.settled_at` is now stamped for capture+accept too (it was settlement only).
- **D11, payment methods.** The console already had a per-method checkbox (Owner only, audited); the default is now ON for every method except `shopeepay`,
  `bri_va`, `cimb_va` and `kredivo` (`sql/seed.sql`, which also moves an untouched pre-D11 default, never an admin's list). The checkout sends only the enabled methods and
  answers 503 with none enabled; the worker raises a critical `checkout_no_payment_methods` alert (the public app cannot write alerts). The form saves the fee of every row, ticked or not, so a
  switched-off method keeps (or is given) a fee and old orders are still priced; an unticked, blank, never-priced row stays "not configured" rather than becoming a stored 0.
- **QRIS fee mapping.** `midtrans_method_codes('qris')` is `{other_qris, gopay}` (`sql/reports.sql`, re-applied by the migration run), because desktop GoPay arrives as qris.
  When both fees are configured the dearer applies, so a QRIS tile payment is reported at the GoPay fee (an overstatement of the fee, never an understatement).
