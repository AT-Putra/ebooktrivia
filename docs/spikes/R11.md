# R11: WAHA recording against the Owner's instance (US-005)

Date: 2026-11-21. Instance: WAHA **2026.10.1**, engine **WEBJS**, tier **CORE** (`GET /api/version`; browser `google-chrome`, `linux/x64`). The audit that precedes this
recording is [api-audit.md](api-audit.md) (docs URLs, the public OpenAPI of the same version). The fixtures are in `infra/waha-mock/fixtures/` (scrubbed); the mock replays
them and `infra/waha-mock/src/replay.test.ts` pins its answers to them.

**Status, plainly (Owner ruling): the webhook HMAC criterion is NOT met by this recording.** It stays DOCS-ONLY: the headers, the algorithm and the webhook envelopes come from the WAHA docs,
not from a delivery. There is no tunnel and no third-party catcher. It is verified with one real signed delivery on staging (US-014 / US-032), and **US-005 stays `passes: false` until then.**

## How it was recorded

- The API key and the base URL came only from the Owner's gitignored `.env.spikes`. No value is in any fixture, test or document. The instance's API key is an administrator key
  (api-audit.md I2), so the recording script refused the environment endpoint, every `PUT`, and every call that changes a session, and printed only whitelisted fields.
- The instance holds **two sessions**; the other one belongs to another application. Nothing of it was read beyond its existence, and its configuration (webhook URLs, HMAC keys) was never printed.
- Messages went **only to the Owner's TEST phone** (`WAHA_TEST_PHONE`), paced. **Five messages** are in that chat's own-message list: one text, one real PDF (13,264 bytes), two documents that are
  WAHA's 404 page (21,483 bytes, the unfetchable-URL probe, see finding 3) and one empty text (see finding 4). The lead was told and passes it to the Owner. No more were sent.
- Scrub: phone, LID, own number and own LID, push name, session name, message keys, texts, media keys and times are stable placeholders (`628123456789`, `98765432101234@lid`,
  `628111111111`, `300000000000001@lid`, `mock`, `default`, `3EB0` + 18 digits, times from 1760000000). The session `config` (webhook URLs and HMAC keys) is not kept. The raw engine
  `_data` of a message (about 3 KB, 90 to 101 keys) is cut down to the file facts. `replay.test.ts` fails on a long digit run or a real-looking message key in any fixture.
- **Not recorded, and why:** a real webhook delivery. This machine has no public URL, and no tunnel and no third-party catcher was used. The HMAC headers, the webhook
  envelope of `message`, `message.ack` and `session.status`, and a `@c.us` sender are therefore DOCS-ONLY (see "What is still docs-only"). `message.json` holds the RECORDED message as the
  instance stores it (read back through GET) inside the DOCUMENTED envelope, and says so in its `_provenance`.

## Mismatches found, ranked

| # | What | Impact | State |
|---|---|---|---|

### Finding 3 in detail: the two guards (Owner ruling)

WAHA fetches `file.url` itself, from our signed download route, and accepts any answer. So the worker checks the route BEFORE asking WAHA, and the result AFTER:

- **(a) Pre-flight, before every `sendFile`** (`apps/worker/src/delivery/access.ts`, `file-check.ts`, `deliver.ts`, `inbound.ts`). The worker signs its OWN 60-second URL for the same file (its own expiry and, since
  the security review, its own random nonce `n` that the signature covers and the route's download counter is keyed on, so it can never share WAHA's counter of 10 downloads per signed URL, even in the same second)
  and GETs it through the worker's safe-fetch (https only, no private, loopback or metadata address) with a budget of its own, `PREFLIGHT_TIMEOUT_MS` (5 s), never WAHA's request timeout. It expects `200`, `application/pdf`, a `Content-Length` equal to the stored size, and
  a body starting `%PDF-`. Anything else is **not attempted** (`file_unavailable`): the delivery goes back to pending, the number's health is not touched (only WAHA's own answers count against a number),
  a persisted critical `delivery_not_attempted` alert is raised (key `delivery_not_attempted:file_unavailable`), and the e-mail path is unaffected. The same check guards the D6 PDF-only reply.
- **(b) Read-back, after a successful `sendFile`.** The worker reads the message back (`getMessage`) and compares `_data.size` (the adapter exposes it as `mediaSize`) with the stored file size. A mismatch
  marks the delivery `sent` with `last_error = delivered_wrong_file` and raises a persisted critical `delivery_wrong_file` alert (the Owner sees it in the delivery report, US-029). It is **never resent
  automatically**. An unknown size is only a debug log (the read-back is best effort). It has a budget of its own, `READBACK_TIMEOUT_MS` (3 s, `getMessage` takes a per-call `timeoutMs`), and is
  skipped when what is left of the claim's lease cannot cover it. Both budgets are in the lease floor (`leaseFloorMs`, `apps/worker/src/delivery/config.ts`: now 202.5 s at the default 60 s request
  timeout; the default lease is 210 s), and the lease check before the pre-flight reserves them.
- Tests: `apps/worker/test/delivery-file-check.int.test.ts` runs both against the mock in `fetchFiles: "webjs"` mode (the mock now answers exactly like WEBJS: a 404 page is delivered as the document).

## What else the recording showed

- The raw send answer is about 3 KB (`_data` carries 90 to 101 keys): the adapter reads only `id`, `timestamp` and `ack`.
- A message KEY on WEBJS is 22 upper-case hex digits (`3EB0...`); the id is `true_<chat>_<key>` for ours and `false_<chat>_<key>` for the buyer's.
- A file message carries `mediaKey` in the raw answer and `_data.size` (bytes delivered) and `_data.filename` in the read-back: the basis of guard (b).
- The mock's session answer is the recorded one (config omitted; `me.reachoutTimelock`, `me.messageCapping`, `presence`, `timestamps`, `engine`).
