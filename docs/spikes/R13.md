## 1. Separate schemas and distinct cookies — PASS

`database: { dialect: new PostgresDialect({ pool }), type: "postgres", schemaName: "player_auth" }` works; the migration begins with `create schema if not exists "player_auth"; create table "player_auth"."user" (...)`.
```
tables by schema: {"admin_auth":["account","session","user","verification"],"player_auth":["account","session","user","verification"]}   (nothing in public)
```
Player `user` gets `phoneNumber text unique`, `phoneNumberVerified boolean` from the plugin. `email` and `name` are NOT NULL, so players need a placeholder email (e.g. `<phone>@players.invalid`) when we create them.

Cookies (`advanced.cookiePrefix`):
```
admin: adm.session_token
player: play.session_token=...; Max-Age=604800; Path=/; HttpOnly; SameSite=Lax
```
**`__Host-` is achievable, but not with `useSecureCookies: true`:**
```
A) useSecureCookies:true + cookies.session_token.name="__Host-play_session"
   -> "__Secure-__Host-play_session=...; Secure"      (BAD: browsers ignore __Host- when it is not the leading prefix)
B) useSecureCookies:false + cookies.session_token = { name: "__Host-play_session", attributes: { secure: true, path: "/" } }
   -> "__Host-play_session=...; Max-Age=604800; Path=/; HttpOnly; Secure; SameSite=Lax"   (no Domain: valid __Host-)
   -> GET /get-session with that cookie: 200, session resolves
```
Recipe: B. Do not enable `crossSubDomainCookies` (it sets `Domain`, invalidating `__Host-`). Also name `session_data`/`dont_remember`/`account_data` the same way if `cookieCache`/rememberMe are ever used. Behind plain HTTP in dev the `Secure` cookie is not stored by non-localhost browsers; make the name configurable per environment.

## 2. OTP storage — PASS only with the workaround (stock storage is plaintext)

Stock `/phone-number/send-otp` always writes the verification row before calling `sendOTP`, whatever `verifyOTP` is.
```
storeIdentifier=plain : {"identifier":"phone-number-otp-+6281200000001","value":"206451:0"}
storeIdentifier=hashed: {"identifier":"_9u2Ri0C00XouuTlZkJRxvVAy5yUPEER_ZDuLWCIFFM","value":"419062:0"}
```
- `verification.storeIdentifier: "hashed"` hashes **only the identifier** (SHA-256 base64url, `db/verification-token-storage.mjs`). The **value is the plaintext code plus `:attempts`** in both modes. The code is also in plaintext in the DB.
- Supplying `verifyOTP` does not stop the stock endpoint from persisting the plaintext `code:0` row.
- With a secondaryStorage configured, the same plaintext row is mirrored there even with `verification.storeInDatabase: true` (key `<prefix>verification:phone-number-otp-<phone>`, JSON with `value: "NNNNNN:<attempts>"`, TTL 299 s). So it also lives in Valkey.

**Workaround (tested):** `hooks.before` on `/phone-number/send-otp` answers the request itself (the plugin endpoint never runs), so no verification row is ever created. Our `enqueueOtp` generates the code and stores `HMAC-SHA256(pepper, phone:code)` in `spike.spike_otp` (phone PK, mac, expires_at, attempts) and hands the plaintext code only to delivery. `/phone-number/verify` stays the stock endpoint, with `verifyOTP` pointed at our store (atomic `UPDATE ... attempts+1 ... RETURNING mac`, `timingSafeEqual`, `DELETE ... RETURNING` for single use).
```
gated send-otp: 200 {"message":"code sent"}
verification rows: []                       spike_otp: [{"phone":"+6281200000001","mac_hex":"f603448f...f7d7","expires_at":"...","attempts":0}]
verify wrong code  -> 400 {"message":"Invalid OTP","code":"INVALID_OTP"}
verify right code  -> 200 + session (user exists)
verify replay      -> 400 INVALID_OTP
3 wrong attempts   -> attempts=3 (further tries rejected by the UPDATE guard)
```
Caveat: a 6 digit code has 10^6 values, so an HMAC row is brute-forceable offline by anyone who has both the DB and the pepper; the pepper must stay out of the DB (env/secret). The value of the HMAC is that a DB-only leak (backup, replica, SQL injection) does not reveal live codes.

## 3. Sign-up disabled — PASS

`signUpOnVerification` omitted: a **valid** OTP for a phone with no user returns
```
POST /phone-number/verify -> 500 {"message":"Failed to update user","code":"FAILED_TO_UPDATE_USER"}   no Set-Cookie
user rows: 0   session rows: 0
```
(the OTP is still consumed). Contrast with `signUpOnVerification` set: same call returns 200 and creates a user row. Other paths: `/sign-up/email` -> 400 `EMAIL_PASSWORD_SIGN_UP_DISABLED`, `/sign-in/email` -> 400 `EMAIL_PASSWORD_DISABLED` (defaults, `emailAndPassword` not enabled). The stock `/sign-in/phone-number`, `/phone-number/request-password-reset`, `/phone-number/reset-password` are switched off with `disabledPaths` -> 404 (see security note 1 for why that is needed).
Players must therefore be created by our own code (`internalAdapter.createUser`, source `phone-number`) when eligibility is established. Note: a user created with `phoneNumberVerified: false` and a non-null `phoneNumber` via the internal adapter outside a request context ended with `phoneNumber: null` (the plugin's `user.create.before` hook nulls an unverified number); create them with `phoneNumberVerified: true` or set it in the same trusted flow. In the tests users are created with `phoneNumberVerified: true`.

## 4. Eligibility gating and uniform response — PASS

`hooks.before` (`createAuthMiddleware`) on `/phone-number/send-otp` calls the stub `enqueueOtp(phone)`; for a non-eligible phone it returns `ctx.json({ message: "code sent" })` — returning a value from a before hook short-circuits the endpoint. Two modes tested:
```
shortcircuit: non-eligible 200 {"message":"code sent"} | eligible 200 {"message":"code sent"} | sendOTP calls: 0 / 0
passthrough : non-eligible 200 {"message":"code sent"} | eligible 200 {"message":"code sent"} | sendOTP calls: 0 / 1
```
Asserted in both: for the non-eligible phone `sendOTP` is not called, no `verification` row, no `spike_otp` row; status, body (byte-identical), `content-type` and `Set-Cookie` equal the eligible response. `passthrough` is NOT recommended (the stock endpoint then stores a plaintext row, see 2); use `shortcircuit`.

## 5. Rate limiting — PASS

Config: `rateLimit: { enabled: true, storage: "secondary-storage", customRules: { "/phone-number/send-otp": { window: 60, max: 3 } } }` plus `advanced.ipAddress.ipAddressHeaders: ["x-forwarded-for"]`. (`rateLimit.enabled` defaults to production only.)
```
5 requests from one IP: [200,200,200,429,429]      sendOTP calls: 3
429: {"message":"Too many requests. Please try again later."}  header X-Retry-After: 60
other IP: 200
```
Valkey keys under the `public` ACL user (`~rl:* ~cache:*`):
- `@better-auth/redis-storage` takes `keyPrefix`; with `keyPrefix: "rl:"` every key it writes is `rl:*`, which the ACL allows. Keys observed: `rl:203.0.113.7|/phone-number/send-otp ttl=60`, `rl:203.0.113.7|/phone-number/verify ttl=60`, plus the mirrored `rl:verification:phone-number-otp-...` (ttl 299, finding in 2).
- A single prefix is applied to everything the secondary storage carries (rate-limit counters, mirrored verification values, and sessions if `storeSessionInDatabase` is false). To keep rate-limit keys apart from the rest, use `rateLimit.customStorage`: tested with `{ consume }` implemented as an atomic Lua `INCR`+`EXPIRE` on `rl:<key>` -> `[200,200,200,429,429]` and the **only** Valkey key is `rl:198.51.100.9|/phone-number/send-otp`. Recommended: `customStorage` for rate limits, no `secondaryStorage` at all (sessions and verification stay in PostgreSQL).
- Out-of-pattern write by `public`: `NOPERM No permissions to access a key` (ACL enforces confinement).
- The `@better-auth/redis-storage` increment/getdel use `EVAL`; allowed for `public` (`+@all -@dangerous -@admin`). ioredis' ready check issues `INFO`, which `public` may not run: set `enableReadyCheck: false` (otherwise a warning only).
- The limiter key is `ip|path` only. `customRules` functions get the `Request`, not a per-phone key, so **per-phone throttling must be done in our `enqueueOtp`** (silently dropping, to keep the uniform response). Test not run for per-phone counters.
- When no IP header is present all traffic shares one `no-trusted-ip` bucket: the proxy must set the header and `ipAddressHeaders` must list only a proxy-controlled header.

## 6. Custom magic-link plugin — PASS

`createAuthEndpoint("/phone-magic-link/consume", { method: "POST", body: z.object({ token }) }, ...)` registered as a plugin: atomic `UPDATE spike.spike_magic_link SET consumed_at = now() WHERE token_hash = $1 AND consumed_at IS NULL AND expires_at > now() RETURNING user_id`, then `ctx.context.internalAdapter.createSession(user.id)` and `setSessionCookie(ctx, { session, user })` (from `better-auth/cookies`).
```
stored row: token_hash (sha256 hex) only; raw token not present
consume #1       -> 200 {"status":true,"userId":"..."} + Set-Cookie play.session_token (get-session resolves the phone's user)
consume #2       -> 401 {"message":"invalid or used link"}, no cookie
unknown token    -> 401, body identical to #2
8 concurrent     -> [200,401,401,401,401,401,401,401]
```

## DECISION: Better Auth player instance (with documented workarounds)

Use Better Auth 1.7.19 for player sessions in schema `player_auth`, with:
1. `phoneNumber` plugin for `/phone-number/verify` and the user/session model, `signUpOnVerification` omitted, `disabledPaths` for `/sign-in/phone-number`, `/phone-number/request-password-reset`, `/phone-number/reset-password`.
2. `hooks.before` on `/phone-number/send-otp` in short-circuit mode: our `enqueueOtp` owns eligibility, per-phone throttle, OTP generation and the HMAC-only `otp` table; stock `sendOTP` throws/never runs.
3. `verifyOTP` bound to our HMAC store (single use, attempts counter).
4. `rateLimit.customStorage` on Valkey with `rl:` keys; no `secondaryStorage`.
5. Magic-link consumption as our own plugin endpoint.

Justification: the unsafe parts (plaintext OTP, unconditional row creation) are all bypassable through supported extension points (`hooks.before`, `verifyOTP`, `disabledPaths`, `customStorage`), the session/cookie handling stays library-owned, and the fallback (custom OTP/session tables) would reimplement exactly the session layer we gain here. Revisit if a Better Auth upgrade changes `hooks.before` short-circuit behaviour: the gated tests would fail, so pin exactly and keep these tests as a regression suite.

## Security concerns found
1. **Stock routes leak/bypass if left enabled.** `/phone-number/request-password-reset` writes a verification row for ANY phone (even unknown) before checking the user; `/phone-number/send-otp` stock endpoint writes plaintext code rows and has no existence/eligibility check at all. Disable or gate every one of these.
2. **Plaintext OTP persisted** by stock flow in PostgreSQL and (with secondaryStorage) in Valkey; `storeIdentifier: "hashed"` does not help (only the identifier is hashed).
3. **Enumeration through `/phone-number/verify` with the stock verifier (from code reading of `verifyPhoneNumberOTP`, not exercised in a test):** `OTP_NOT_FOUND` (no code issued) vs `INVALID_OTP` (code issued, wrong) differ; with our `verifyOTP` both cases return `INVALID_OTP` 400 (tested: wrong code, replay). Only a correct OTP on a phone with no user returns 500 `FAILED_TO_UPDATE_USER`, which cannot occur for a non-eligible phone because no code exists. Make the 500 a generic 400 via an after hook if desired.
4. **Timing side channel (not measured):** the eligible path does DB writes and enqueue while the non-eligible path returns immediately. Mitigation: do the same amount of work (or enqueue asynchronously and always return after a fixed minimal delay).
5. **IP rate limit is the only built-in limiter**; per-phone throttle (OTP-bombing a single victim from many IPs) must be ours. The 429 is IP-based and identical for eligible and non-eligible phones, so it does not leak eligibility.
6. **`x-forwarded-for` trust:** an attacker-controlled header defeats the limiter unless the edge proxy overwrites it.
7. **Verify consumes the OTP before failing** on a missing user (500), so an eligible phone whose user row was not yet created loses its code; create the user before issuing the OTP.
8. **Placeholder email:** `user.email` is NOT NULL UNIQUE; use a deterministic `<phone>@players.invalid`.
