## Instance observations (not code mismatches)

- **I1** The Owner's instance holds TWO sessions, both `WORKING`; the other one belongs to another application. Each session has a webhook configured for that other application (`events: ["message"]` only). `PUT /api/sessions/{session}` REPLACES the whole `config`, so adding our webhook (`message`, `message.ack`, `session.status`, with our own HMAC key) must keep the existing entry, or that application stops receiving messages.
- **I2** `GET /api/sessions` and `GET /api/sessions/{session}` return the session `config`, including every webhook URL and its HMAC key. `GET /api/server/environment` answers (with only the API key) the dashboard and Swagger passwords. The API key is therefore an administrator key of the instance: store it as one (our sealed secret is right), and never let a log carry a WAHA answer in full.
- **I3** Our webhook events list must include `message` (incoming only), `message.ack` and `session.status`; `message.any` is not needed.

## Findings from the Midtrans recording that were not in the docs (R12)

- **Status after the Owner's rulings (D9 to D11, R12.md and docs/runbooks/payments.md): M15 and M20 are implemented (a paid order whose counted payment Midtrans reverses goes to review with a critical alert; capture + accept is paid), M21 is fixed in `sql/reports.sql`, M23 is the per-method switch with the four codes off by default.**
- **M20 (card capture, Owner decision).** A successful card payment is `capture` + `fraud_status accept` + `status_code 200` (with `settlement_time` already set), not `settlement`. `confirmSettlement` accepts it only with `treatCardCaptureAsPaid` (default off) and `recordPayment` stamps `settled_at` only for `settlement`: with the default a card buyer is "not paid" until the next day. The docs call `capture` safe to treat as paid.
- **M21 (fee code gap) FIXED.** Desktop GoPay and plain QRIS both arrive as `payment_type: "qris"`; `midtrans_method_codes('qris')` is now `{other_qris, gopay}` (`sql/reports.sql`, re-applied by the migration run: no migration), so a payment through the `gopay` tile is priced with its fee; with both fees set the dearer applies.
- **M22 (expired order ids).** An order id expired through the API is still refused on a new create (the docs say it can be reused): our `{publicId}-{n}` scheme is unaffected.
- **M23 (four codes not offered).** `shopeepay`, `bri_va`, `cimb_va` and `kredivo` are accepted by Snap create but not offered on the Snap page of the Owner's sandbox account (an invented code behaves the same).
- **M24 (3-D Secure, security review).** The Snap request now carries `credit_card: { secure: true }` whenever cards can be offered: the Owner's sandbox account does NOT default to 3DS (docs/spikes/R12.md, "3-D Secure"), whatever the docs' "default true" says.

## Findings from the WAHA recording that were not in the docs (R11)

Details and the answers to every open question are in [R11.md](R11.md). Ranked:

- **W1 (HIGH, FIXED).** A WEBJS send answers the raw whatsapp-web.js message with an OBJECT `id`; `sent()` now reads `id._serialized`. Before this, every send on the Owner's instance would have been judged `maybe_sent`.
- **W18 (HIGH, FIXED).** WAHA does not refuse a file URL it cannot fetch: it sends the 404 page as the document and answers `201`. US-025's "422 on fetch failure" is FALSE for WEBJS. Two guards (Owner ruling): a pre-flight of the worker's own 60 s signed URL before every send (`file_unavailable`, not attempted, alert), and a read-back of the delivered size after it (`delivered_wrong_file`, alert, never resent).
